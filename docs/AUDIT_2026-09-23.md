## 시험 장치 보강 (G 갈래 심사 반영)
- `hard_reset()` — RAM 전역을 전부 다시 만드는 **진짜 리셋**(EEPROM·RTC 칩·카드는 유지). 2차의 `reboot()` 는 `setup()` 만 다시 불러
  RAM 플래그가 살아남았고, 그래서 첫 번째 결함을 못 봤다. 이제 `t_clear`·`t_firstboot`·`t_disinfect` 가 리셋 사이 동작을 본다.
- 가짜 카드: `PICC_WakeupA`(HALT 도 응답), `readErrSkip`(처음 n회 읽기는 통과 — 쓰기 확인 읽기만 실패시킬 때).
- 안 잠겨 있던 자리 셋을 잠금(각각 되돌린 변이에서 빨강 확인): 환자 키·이름 16바이트 저장 · 담당자 미등록 거부 · 게이트웨이 `Status=1` 커밋 순서.
- 부정 확인(`!clear_is(…, 분)`) 둘을 "표지 날짜인가" 로 바꿔 시각에 흔들리지 않게.
- 가짜가 실물과 다른 곳·이 장치가 증명 못 하는 가정 넷은 `tools/sim/README.md` 에 적었다 — **실기 확인 우선순위**:
  ① 정지 못 시킨 카드의 REQA 응답 패턴(디바운스 근거) ② 인증 실패 뒤 카드 상태 ③ 리더 재초기화가 올려 둔 태그를 재처리하는가
  ④ CRC 오류 뒤 nested 재인증 실효 ⑤ NACK 뒤 재시도.

## 세척관리(TraceQ_Python) 쪽 (F 갈래)
- 검사명 조각 셋을 `' '` 로 이어 붙여 "상부위장관내시 경검사" 처럼 엉뚱한 자리에 공백 → `''.join`(델파이 원본과 같음).
  `tests/regression/v_examsubj.py` — 실제 덤프 줄을 실제 파서에 넣어 SeePro 15바이트·올눈 16바이트 조각 모두 원문 그대로.

## 결함 아님 / 판정 유지
- 게이트웨이 수신 1초로 두 G 패킷이 한 버퍼에 오는 창(2차 P3) — 송신기 셋 전수로 미도달.
- 펌웨어 버전을 PC 가 알 방법 없음(2차 P3) — PC 가 버전별로 달리 행동할 분기가 없고 LCD 홈 3행·업로더 파일명으로 현장 확인.
- 더블터치 재시작 뒤 소독 횟수: "커밋됐지만 확인 실패" 뒤의 재시작은 횟수를 올리지 않아 **1회 적게** 셀 수 있다(기기 횟수는 최대 횟수 경고용, 현장 집계는 세척관리 몫). 상태를 늘려 맞추지 않는다.

## P3 (목록만 — 갈래 보고서 참조)
같은 번호의 다른 태그가 2초 안 재시작 · 시계를 뒤로 돌리면 종료된 태그까지 재시작 · 손상 연도 2047 고착 · `TRACEQ_RELEASE_*` 를 미래로 잘못 올리면 미룸이 영영 안 풀림 ·
디바운스 창 2폴 안 카드 교체 시 K 갇힘 · 죽은 리더 Reinitialize 루프당 ≈0.3s · 더블터치 판정이 세척·소독 두 벌(같은 helper 를 부르므로 갈라질 자리는 호출 두 줄) ·
매 루프 `now()` I2C ≈1ms · 리터럴 흩어짐(2초·127·17) · 올눈 `StrLenCut` 오프바이원(남은 ASCII 1자 유실 — 올눈 쪽) · Configurator 가 클램프 값을 되읽지 않음 ·

# v2.2.9 — 실패를 소리로 알린다 (사장님 지시, 09-23 저녁)

3차 감사 뒤 사장님 지시로 추가한 것. 계기: **기독병원 "소리는 정상으로 났는데 서버에서 '세척 정보가 없습니다'"**
— 2.2.6 은 세척 시작 기록이 실패해도 완료음을 내고 알람까지 걸어, 담당자는 정상으로 알고 넘어갔다.
그 음성은 PC 가 지어낸 것이 아니라 **리더기가 보낸 `Not Washing` 을 그대로 읽어 주는 것**(구형 델파이
`MainFormSo.pas:5864` → `Sound\05-세척정보가없습니다.wav`, 세척관리 `_on_scan_rejected` — 같은 트리거).
1.4.1↔2.2.x 덤프 형식·블록 키는 바이트까지 같아 **PC 호환 문제가 아니었다.**

## 1) 기록이 안 됐으면 완료음이 나지 않는다
2.2.8 은 세척·소독 **시작**만 막혀 있었다. 나머지 자리를 전부 맞췄다 — 세척·소독 **종료**, 소독 **이동**,
게이트웨이 **본 경로·폴백**, 서버 **덤프 뒤 소거**, **담당자 등록**, 그리고 **태그 읽기 실패**(세척·소독·서버·
게이트웨이 네 갈래 + 진입 단계). 실패하면 LCD 에 `Write Error`/`Read Error`, 실패음, **알람·커밋·성공음 없음.**

## 2) 소리 규칙 — 부저는 한 소리뿐이라 리듬으로 가른다
| 소리 | 뜻 | 담당자가 할 일 |
|---|---|---|
| 짧게 1회(50ms) | 정상 | 진행 |
| 길게 2회(400ms) | 환자정보 없음(기록은 됨) | 진행해도 됨 |
| 짧게 4회(100ms) | 기록 실패 | **다시 대기** |
| 삐삐 + 긴 삐(60×2 + 600) | 거부(여기선 안 되는 태그) | 앞 단계 확인 |

종전엔 세척기의 "환자정보 없음"과 "기록 실패"가 **같은 소리**였고, 같은 뜻인데 세척기(100ms×4)와
소독기(40ms×4)가 **서로 달랐다**. 거부는 `LcdPrinter::Reject`/`RejectDebug` 로 모았고 **시리얼 문자열은 불변**.

## 3) 서버 덤프 뒤 초기화 순서 — 세 불변식
환자정보표시 내림 → 게이트웨이·검사항목 소거 → **완료 커밋** → 환자 블록 소거.
① "환자정보 있음인데 블록은 빈" 태그를 안 남긴다(그런 태그는 세척기 미기재 경고를 무력화).
② 커밋 전 실패는 재접촉으로 복구된다. ③ 2차 덤프가 **빈 환자정보로 PC 기록을 덮어쓰지 않는다**
(구형 델파이는 등록번호로 중복을 가린다 — 비면 가드를 통과해 36필드를 덮어썼다).
덤프 뒤 쓰기 8곳 전수 확인. 성공 결과는 1.4.1·2.2.8 과 **바이트 동일**(카드 64블록 해시 대조).
★내가 이 순서를 두 번 틀렸다: 2.2.8 순서는 재접촉이 영영 거부됐고, 낮에 고친 순서는 PC 기록을 덮어썼다.

## 4) 업로드할 때 설정 유지 / 완전 초기화 선택 (1.4.1 병원 대응)
쓰던 기기면 첫 부팅에 `Keep settings?` — **SELECT=유지 / RIGHT 0.2초 이상=완전 초기화 / 10초 무응답=유지.**
공장 기기(타입 원값이 W/D/S/G 가 아님)는 묻지 않고 초기화. **전원 켤 때 RIGHT 을 누르고 있으면 같은 판에서도
다시 고를 수 있다**(유지를 고른 뒤 되돌릴 유일한 길 — 메뉴·설정 프로그램·클리어 태그로는 초기화 불가).
1.4.1 과 EEPROM 주소가 전부 같아 유지하면 기기번호·세척시간·담당자·소독 횟수·**액교환일**이 그대로 남는다.
177번지(2.2.7 신설)는 **알 수 없는 값일 때만** 정리 — 정상 미룸(1·2)은 시계를 못 맞춘 기기이므로 보존.

## 시험 장치 (검토 두 갈래가 잡아낸 것)
- **RAM 가드가 실제로는 막지 못했다** — 정상 빌드도 항상 실패 코드를 냈고(마지막 줄 `[ -n ... ] && exit 1`),
  한도를 넘겨도 `.elf` 가 남아 runall 이 그대로 돌렸다. 이제 초과 시 elf 삭제 + exit 1, 정상 exit 0(실증).
- **로그가 잘려 FAIL 이름이 통째로 사라졌다** → 실패 전용 버퍼 `g_failLog`. 실제로 이 덕에 내 기대값 오류를 찾았다.
- **오늘 넣은 읽기 실패 알림 3자리가 아무 시험에도 안 잡혔다**(헛초록) → 시험 신설, 지우면 빨강 확인.
- 고장 주입을 **중간 쓰기**로 옮겨 "자명하게 참"이던 확인을 실질화. 카드는 2~4장 돌려쓰기(RAM).
- 시뮬 RAM 은 31.5KB 고정 — 스택을 0xFFFF 로 올리면 t_issue 가 전멸한다(직접 확인, 되돌림).

빌드: RAM 3,018 B · Flash 49,496 B · 경고 0 · 시뮬레이터 10종 **214 CHECK 초록** · 세 빌드 환경 통과.
